## 一、开发铁律（不可违反）

| # | 铁律 | 违反后果 |
|---|------|---------|
| 1 | **写代码前先CRG建图**：`code-review-graph build`，查影响半径 | 🔴 直接打回 |
| 2 | **先写测试再写代码**（TDD） | 🔴 直接打回 |
| 3 | **不能把代码提交到生产站**，必须先上开发站测试 | 🔴 直接打回 |

## 二、开发全流程

### 流程全景

```
[需求] → [讨论] → [计划] → [写代码] → [自查] → [审核] → [合入开发站] → [老板确认] → [上线]
```

### 详细步骤

#### 步骤0：选型调研（新项目必过）

当接到新项目时：

1. **第1天**：弄清楚要解决什么问题、有没有现成方案
2. **第2-3天**：查资料，竞品怎么做的、技术栈对比
3. **第4-5天**：问团队意见
4. **第6天**：出选型文档，@所有人确认
5. **第7天**：才能开始写代码

**绝对禁止：** 项目下来就立刻写代码。

#### 步骤1：建图（第一个动作）

进入仓库后先建依赖图：

```bash
cd ~/你的仓库
code-review-graph build
code-review-graph status   # 确认有节点数
```

**查影响半径（改代码前）：**

```bash
# 改之前，查改了A会影响哪些文件
code-review-graph detect-changes --repo ~/你的仓库 --base HEAD~1
```

#### 步骤2：写计划

每项任务必须细到**2-5分钟**能做完，格式：

```
### Task N: 描述

文件：
- 创建: exact/path/file.py
- 修改: exact/path/file.py:行号

步骤1：写测试
步骤2：确认测试报错
步骤3：写最小实现
步骤4：确认测试通过
步骤5：提交（git commit -m 'feat: xxx'）
```

#### 步骤3：TDD 写代码

**必须严格遵循 RED → GREEN → REFACTOR：**

```
① RED：先写测试 → 运行 → 确认失败（证明测试有效）
② GREEN：写最简代码 → 运行 → 确认通过（不追求质量）
③ REFACTOR：清理代码 → 运行 → 确认无回归

每行为一个功能点，一个功能点一个循环
```

**不允许：**
- ❌ 先写代码再写测试（立即删除重来）
- ❌ 一次写多个功能再测试
- ❌ 写了代码不改测试

#### 步骤4：自查（必须自己先测）

改完后，在提交前必须执行自查清单（6项）：

| 检查项 | 标准 |
|--------|------|
| 安全扫描 | 无硬编码密码、无SQL拼接 |
| 影响半径 | CRG detect-changes无意外影响 |
| 中文注释 | 每个public方法有DocBlock，复杂逻辑有行内注释 |
| 拼音变量 | 禁止 `$sj`、`$fwq`、`$bh` 等缩写 |
| 95线 | 无遗留 `print/console.log/echo` |
| 自测 | 浏览器自己走一遍全流程 |

**红线（审核直接打回）：**
- 🔴 硬编码密码/token
- 🔴 SQL字符串拼接
- 🔴 10行以上无注释函数
- 🔴 拼音变量名
- 🔴 遗留debug语句

#### 步骤5：提交

```bash
git add -A
git commit -m '[verified] type: 做了什么'
```

提交信息格式：`[verified] type: 做了什么`

#### 步骤6：推送到GitHub

```bash
git push origin main
```

如果不配token推不动，找chaogu-ai处理。

## 三、代码质量要求

### 语言规范

| 语言 | 规范 |
|------|------|
| **Python** | PEP 8，函数/类有docstring，类型注解 |
| **Go** | gofmt，error处理不吞，goroutine有生命周期管理 |
| **Java** | Google Java Style，Lombok可接受 |
| **PHP** | PSR-12，ThinkPHP遵循框架规范 |
| **SQL** | 全部参数化，关键字大写，表名/字段snake_case |
| **TypeScript** | ESLint + Prettier，严格模式 |

### 注释规范

- 所有注释用**中文**，说清楚**为什么**这么做（不是做了什么）
- public方法必须有DocBlock/DocString
- 超过10行的函数必须有行内注释
- 复杂的业务逻辑必须写注释

### 命名规范

- ✅ 英文有意义的命名：`auth_service`、`get_user_by_id`
- ❌ 拼音缩写：`$sj`（时间）、`$fwq`（服务器）、`$bh`（编号）
- ❌ 单字母：`$a`、`$b`、`$x`
- 数据库表名/字段：全部小写+下划线（snake_case）

### 错误处理

- 所有I/O操作必须有 try/catch 或 error check
- 不能吞错误（不能 `except: pass`）
- 外部调用（API/DB/文件）必须处理超时和重试
- 日志要写清楚：谁、什么时候、什么参数、什么结果

### 安全红线

| 红线 | 说明 |
|------|------|
| 硬编码密码/API key | 一律走环境变量 `.env` |
| SQL拼接 | 必须参数化查询 |
| eval/exec用户输入 | 禁止 |
| XSS输出 | 前端必须转义用户输入 |
| CSRF | 接口必须校验token |
| 文件路径遍历 | 用户输入不能直接拼路径 |
| 不安全的反序列化 | 禁止 `pickle.loads(user_input)` |

## 四、调Bug流程

### 4步法（必须按顺序）

**第一步：根因分析（不找根因不准动手）**
- 仔细读错误日志（不是瞟一眼）
- 复现问题（重复能触发的才是bug）
- 查最近改了什么（git diff / git log）
- 追踪数据流：入口 → 处理 → 输出，在哪里坏的
- **必须找出根因，不能猜**

**第二步：模式分析**
- 找代码库里相似的、能正常工作的写法
- 对比：正常的和坏的区别在哪里？
- 逐项列出差异，不假设"这个不影响"

**第三步：假设测试**
- 1次只改1个变量
- 改完验证，不生效就换假设
- 如果试了**3次还不行** → 停下来，可能是架构问题

**第四步：修复**
- 先写回归测试（TDD方式）
- 改根因，不改症状
- 跑全量测试确认无回归

### 特殊：多人故障

当多个服务同时出问题时（微信+企微+VPN一起挂）：
- 大概率是**网络问题**，不是应用配置问题
- 先查网络再查应用

## 五、版本管理

### 版本号格式

```
vYYYYMMDD-N
```

示例：`v20260603-1`、`v20260603-2`（每天从1开始）

### 每次修改必须

1. commit到git（加版本号tag或commit message带版本号）
2. 标注改了哪些文件
3. 测试通过

### 回退流程

1. 老板说"退回到版本X"
2. git revert 或替换备份文件
3. 重启服务确认可用
4. 汇报老板

## 六、分支策略

| 分支 | 用途 | 谁推 |
|------|------|------|
| `main` | 生产稳定版 | 审核后由负责人合入 |
| `dev` | 开发主分支 | 开发者 |
| `feature/xxx` | 功能分支 | 开发者 |
| `docs` | 文档分支 | 文档维护者 |

- **开发站测试 → `dev`**
- **生产站上线 → 老板确认后合入 `main`**

## 九、常用命令速查

### CRG（代码依赖图）

```bash
code-review-graph build                         # 首次建图
code-review-graph status                        # 查图状态
code-review-graph detect-changes --base HEAD~1  # 查本次改的影响范围
code-review-graph update                        # 增量更新
```

### Git

```bash
git status
git log --oneline -5
git diff --stat
git add -A && git commit -m '[verified] type: 说明'
git push origin main
```

### 自查

```bash
# 高级工程师专用
bash ~/code-review.sh

# 通用——检查是否有密码泄露
git diff --cached | grep "^+" | grep -E "(api_key|password|secret|token)\s*=\s*"
```

## 十、常见错误与预防

| 场景 | 正确做法 | 错误做法 |
|------|---------|---------|
| 服务器挂了 | 先查网络（ping/curl）再查应用 | 直接重启应用 |
| 任务卡住了 | 群里问其他bot帮忙 | 一个人死磕 |
| 需要装新包 | 通知对应的运维bot | 自己装卡半小时 |
| 测试不通过 | 用TDD查具体哪个断言失败 | 随便改一行重新跑 |
| 多个服务同时挂 | 先查网络（gateway路由有没有变） | 逐个排查应用 |
| GitHub推不动 | 找chaogu-ai配token或用SSH key | 不推送 |
| 怕改出问题 | 先git commit打版本号 | 直接改不备份 |
