# 12FZ 统一身份与命名规范 v2.0（设计草案）

> 未上线窗口一次性重构 · 2026-08-15
> 目标：按大厂行业惯例（IAM 标准）彻底解决 user_id/org_id 混淆与命名不规范问题

---

## 一、设计原则（大厂行业惯例）

1. **身份域独立**：用户/账号/租户/权限归 `iam` schema，与业务域解耦
2. **uid 全局唯一**：用户 ID 用 `uid`（BIGINT），取代 `user_id`（和 org_id 混淆的根源）
3. **租户模型**：组织/商户统一叫 `tenant_id`（UUID），取代泛义的 `org_id`
4. **账号与用户分离**：`accounts`（登录凭证）独立于 `users`（身份）——一个用户多登录方式（密码/手机/微信）
5. **归属双维度**：业务数据统一 `tenant_id`（哪个租户）+ `owner_uid`（哪个用户）
6. **uid 值不重排**：原 `org_user.user_id` 值直接继承（1=admin 不变）——历史引用不断

## 二、设计依据（为什么这么选——讨论用）

### 2.1 为什么 `uid` 而不是 `user_id`
| 依据 | 说明 |
|---|---|
| **混淆根源** | `user_id` 与 `org_id` 一字之差，代码/文档/聊天里高频并列出现（如 `org_user` 表里同时有 user_id 和 org_id），阅读要停一下才能分清"用户"还是"组织" |
| **行业惯例** | `uid` 是互联网通用术语（微信/游戏/各大平台），3 字母无歧义，现有代码（sso.go SignJWT(uid)）已在使用 |
| **类型统一** | chat 表 `user_id` 存 text（"1"），org_user 存 int（1）——同一概念两种类型；改 uid（BIGINT）一次性统一 |

### 2.2 为什么 `tenant_id` 而不是 `org_id`
| 依据 | 说明 |
|---|---|
| **org 语义太泛** | org 可指组织/机构/商户/公司；`org_user` 表名还误导（像"组织用户关联表"，实际是用户主表） |
| **大厂标准** | 多租户 SaaS 的隔离单元标准词是 tenant（阿里云/飞书/钉钉均用 tenant 模型）；商户 = 租户的一种 |
| **扩展性** | 将来多商户入驻、RLS 隔离、账本分账按 tenant 维度天然清晰，不需要再造概念 |

### 2.3 为什么 `iam` 独立 schema
| 依据 | 说明 |
|---|---|
| **分层架构** | 身份（iam）/业务（platform）/聊天（chat）/中转（proxy）分域，职责清晰 |
| **权限可扩展** | 标准 RBAC（roles/permissions/user_tenants）为将来多角色、多商户管理员打底 |
| **大厂中台惯例** | 统一 IAM（身份与访问管理）是标准做法——账号/用户/租户/权限集中一处管理 |

### 2.4 为什么 `accounts` 与 `users` 分离
| 依据 | 说明 |
|---|---|
| **一用户多登录方式** | 密码/手机/微信/邮箱——凭证放 accounts，身份放 users——加登录方式不改用户表 |
| **安全隔离** | 密码哈希、登录审计独立管理；微信 openid 不污染用户主表（规则 7 的双锚点天然落位） |

### 2.5 为什么 `uid` 值不重排
| 依据 | 说明 |
|---|---|
| **最小风险** | 1=admin、2=测试、11-14=bot 等现有值原样继承——历史数据/外部引用/文件权限不断 |
| **迁移平滑** | 只改类型和列名，不改业务语义——迁移脚本可验证（数量一致、值一致） |

### 2.6 为什么现在做（一次性）
| 依据 | 说明 |
|---|---|
| **未上线窗口** | Marketplace 业务未正式运营、商户未入驻——改命名=纯内部改动，无客户影响 |
| **越晚越贵** | 上线后改 = 停机 + 兼容层 + 数据迁移 + 客户数据风险——成本 10 倍以上 |
| **消除隐患** | 现在就有 user_id/org_id 混淆导致的改错先例（08-15 归属误判），命名规范是根因治理 |

## 三、目标表结构

### 3.1 身份域（iam schema——新建）

```sql
iam.users
  uid          BIGSERIAL PK        -- 用户 ID（原 org_user.user_id，值不重排）
  name         TEXT                -- 昵称
  status       TEXT DEFAULT 'active'
  created_at   TIMESTAMPTZ DEFAULT now()

iam.accounts                        -- 登录账号（从 org_user 手机/邮箱拆出）
  id           BIGSERIAL PK
  uid          BIGINT NOT NULL REFERENCES iam.users(uid)
  login_type   TEXT NOT NULL        -- password / phone / email / wechat
  identifier   TEXT NOT NULL        -- 手机号 / 邮箱 / openid
  secret_hash  TEXT                 -- 密码哈希（wechat 为空）
  status       TEXT DEFAULT 'active'
  UNIQUE (login_type, identifier)

iam.tenants                         -- 租户/组织（原 org_id 语义）
  tenant_id    UUID PK DEFAULT gen_random_uuid()
  name         TEXT
  type         TEXT NOT NULL        -- platform / merchant / company
  status       TEXT DEFAULT 'active'

iam.user_tenants                    -- 用户-租户关系（替代 org_user 的 org 绑定）
  uid          BIGINT REFERENCES iam.users(uid)
  tenant_id    UUID REFERENCES iam.tenants(tenant_id)
  role_id      BIGINT
  is_default   BOOLEAN DEFAULT false
  UNIQUE (uid, tenant_id)

iam.roles / iam.permissions / iam.role_permissions   -- 角色权限（标准 RBAC）
```

### 3.2 聊天域（chat schema——uid 类型统一 BIGINT）

```
chat.contacts      (uid BIGINT, contact_uid BIGINT)          -- 人↔人
chat.user_agents   (uid BIGINT, agent_id TEXT)               -- 人↔Agent
chat.user_hosts    (uid BIGINT, host_id TEXT)                -- 人↔主机
chat.messages      (sender_uid BIGINT, receiver_uid BIGINT)
chat.hosts         (..., tenant_id UUID)                     -- org_id 改列名
```

### 3.3 业务域（platform schema——统一 tenant_id 列名）

```
platform_orders            (order_id, tenant_id, owner_uid, ...)
platform_finance_ledger    (id, tenant_id, direction, amount_cny, ...)
platform_products          (product_id, tenant_id, ...)
... 41 个 platform_ 表全部 org_id → tenant_id
```

### 3.4 中转域（chat/proxy——tenant_id + uid）

```
chat.proxy_keys      (key_id, key_text, tenant_id, host_id, uid, status)
chat.proxy_usage     (id, tenant_id, uid, model_name, prompt_tokens, comp_tokens, cost, ...)
chat.proxy_pricing   (不变——全局定价)
```

## 四、新旧映射表（迁移依据）

| 现状 | 目标 | 迁移方式 |
|---|---|---|
| `public.org_user` | `iam.users` + `iam.accounts` | 数据搬移；手机/邮箱拆进 accounts |
| `org_user.user_id`（int） | `users.uid`（BIGINT） | **值不变**（1/2/11-14 保留） |
| `org_id`（UUID） | `tenant_id`（UUID） | **值不变**（00000000 平台保留） |
| `chat.*.user_id`（text "1"） | `uid`（BIGINT 1） | text→bigint 类型转换（全表） |
| `chat.hosts.org_id` | `chat.hosts.tenant_id` | 列改名 |
| `chat.proxy_keys.org_id` | `tenant_id` | 列改名 |
| `host_reg_codes.org_id` | `tenant_id` | 列改名 |
| JWT `{uid, username, org_id}` | `{uid, tenant_id, roles}` | payload 重签 |

## 五、迁移步骤（未上线窗口执行）

1. **DDL**：建 `iam` schema + 5 张身份表；业务/聊天表 `org_id` 改 `tenant_id`
2. **数据迁移**：`org_user` → `users`/`accounts`（uid 值不变）；chat 表 `user_id` text→bigint
3. **代码重构**：chat-token + marketplace 全部 SQL/ORM/JWT 适配（uid/tenant_id）
4. **依赖更新**：RLS 策略（41 表列名）、审计触发器、漂移检测脚本
5. **全量回归**：登录/聊天/中转/计费/商户隔离/设备注册（含隔离 8/12 验证）
6. **文档更新**：用户体系规则 v2.0 + Marketplace v3.36

## 六、影响面清单（诚实评估）

| 影响 | 说明 |
|---|---|
| **停机窗口** | 聊天/AI 中转/Hermes/设备在跑——迁移需 30-60 分钟停机（未上线期可接受） |
| **代码量** | chat-token + marketplace 全量列名改动（预计 200+ 处 SQL/字段引用） |
| **风险** | RLS/触发器/审计依赖列名——迁移脚本必须精确，先备份全库 |
| **收益** | 命名永久规范；将来不再有 user_id/org_id 混淆；租户模型扩展（多商户入驻）无障碍 |

## 七、命名规范（后续所有代码强制，进文档 + 代码规范）

| 术语 | 含义 | 禁止 |
|---|---|---|
| `uid` | 用户 ID（BIGINT） | ~~user_id~~（存量迁移） |
| `tenant_id` | 租户/组织 ID（UUID） | ~~org_id~~（存量迁移） |
| `account_id` | 登录账号 ID | — |
| `owner_uid` / `creator_uid` | 操作人 | ~~owner_user_id~~ |
| `login_type` | 登录方式（password/phone/email/wechat） | — |
| — | — | username/昵称当外键（规则 1 延续） |
